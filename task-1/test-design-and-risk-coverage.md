# Task 1 — Test Strategy and Test Cases

## 1.1 — Questions and assumptions

> * Where is the OTP generated? Is it possible to simulate generation malfunction from the server? Assuming the OTP is generated from the same system.
> * What happens If the user doesn't receive the OTP, would there be an option to resend? what's the resend limit?
> * For the testing Engineer: Could the daily limit/fees be configured?
> * For the testing Engineer: Could the balance be manipulated from the database?
> * What are the field validations for the editable fields?
> * Which validations are front-end and which appear on submit?
> * What happens when entering the OTP after time expires? Assuming there is a timer.
> * What happens if a user tries to make the same transaction through 2 different devices at the exact same time?<br/>
    > Note: automation or performance tools could be used for simulation.
> * For the testing Engineer: How to simulate a false positive? This is a common real scenario in case of an internet
    glitch: the transaction is done and debited, however, it is put on hold and never reaches the other party.
> * What if a fee changes, in which time zone shall the new value be applied? Assuming the customer is in a different
    time zone from the beneficiary.
> * If both customer and beneficiary accounts belong to the same person, would the same fee apply?
> * Is there a fee exception for certain types of accounts or certain type of transaction?
> * What if the beneficiary account is blacklisted at any point in the transaction?                                                                                                                                                                                                                                                                                                                                          

## 1.2 — Risk assessment

| Risk                                        | Impact                                                                      | Priority |
|---------------------------------------------|-----------------------------------------------------------------------------|----------|
| OTP validation failure                      | Unauthorized transfers or rejected legitimate transfers.                    | High     |
| Network interruption or transfer failure    | Funds debited without reaching the beneficiary.                             | High     |
| Production database crash during a transfer | Transaction data loss, inconsistent balances, or transfers left incomplete. | High     |

## 1.4 — Coverage decisions

> * Personally, I wouldn't go with only 12 cases to cover such a feature. I would probably create more scenarios to
    cover each requirement in detail, especially boundary values, OTP expiration, concurrent transfers, and transaction
    recovery.
> * According to the answers to my questions above, I would add scenarios to the applicable points.
> * I would automate all scenarios that can be reliably automated. Scenarios requiring backend failure simulation may
    need a controlled test environment or manual execution, depending on the available test hooks. Not all automated
    scenarios would run in a regression suite.
> * Automated regression would mainly include end-to-end scenarios and front-end validations that don't depend on the
    backend. Critical financial rules, including transfer limits and duplicate-transfer prevention, should also be
    included in regression.
